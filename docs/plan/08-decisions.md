# 20. Architecture Decisions

Each ADR records **Decision · Reason · Alternatives · Trade-offs**. Status: *Proposed* until you approve the plan.

| # | Decision | Reason | Alternatives considered | Trade-offs |
|---|---|---|---|---|
| ADR-001 | **Modular monolith** (NestJS) + separate **worker** processes from the same codebase | Fastest path to a coherent product; one transaction boundary for time and money; easy refactors while the domain is still being learned | Microservices from day one; serverless functions | Needs boundary discipline (lint-enforced). Extracting ingestion later is a planned, not a free, effort. |
| ADR-002 | **pnpm + Turborepo monorepo** | Shared types/schemas across web, API, agent, and extension; atomic changes to contracts | Nx; separate repos | Turborepo is lighter than Nx but has fewer generators. One repo means CI must be cached well. |
| ADR-003 | **Next.js App Router** for web, as an API *client* (no domain logic in Next) | Server components for data-dense pages; a mature routing/layout model | Vite SPA (React Router); Remix | Server components add mental overhead. Keeping logic in the API avoids a second backend. |
| ADR-004 | **NestJS on the Fastify adapter** | DI, modules, and guards map onto RBAC and modules; throughput from Fastify | Express; Hono; tRPC-only | Nest's decorators are verbose. Fastify has some plugin-ecosystem differences. |
| ADR-005 | **PostgreSQL 17 as the single transactional source of truth** | ACID for time/money; RLS; partitioning; JSONB; rich SQL for reporting | MySQL; MongoDB; a separate time-series DB for activity | Activity volume needs partitioning discipline. Timescale remains an option. |
| ADR-006 | **Drizzle ORM** with SQL migrations | SQL-first control for RLS `SET LOCAL`, partitions, exclusion constraints, `ON CONFLICT`; types shared with other packages | Prisma; Kysely; TypeORM | Smaller ecosystem than Prisma. Complex migrations are hand-written SQL, which is a deliberate choice. |
| ADR-007 | **Tenant isolation = app-level scoping + PostgreSQL RLS + composite FKs** | Defence in depth: one missed filter cannot leak data | Schema-per-tenant; DB-per-tenant; app-only filtering | RLS adds per-transaction `SET LOCAL` and pooler constraints (transaction mode). Schema-per-tenant was rejected because of migration cost at thousands of orgs. |
| ADR-008 | **Transactional outbox → BullMQ (Redis)** for async processing | Events are never lost when Redis blips; handlers are idempotent | Kafka/Redpanda; RabbitMQ; PG-only queue (pg-boss) | Redis is not the durable log. Replaying from the outbox is possible. Kafka is overkill at launch; the move is documented if throughput demands it. |
| ADR-009 | **Server-authoritative session state machine**; clients send commands and observations | Prevents client tampering and clock skew from corrupting time; one source of truth | Client-authoritative timers that sync totals | Needs careful offline reconciliation logic (seq, skew, bounded offline window). |
| ADR-010 | **Append-only time revisions + approval snapshots** | Auditability; "never silently rewrite history"; billing reproducibility | Mutable rows plus an audit table only | More storage and query complexity. Views expose the "current" revision. |
| ADR-011 | **Screenshots direct-to-S3 via presigned PUT**, metadata in PG | Keeps large binaries off the API and the DB; scales cheaply | Upload through the API; store in PG bytea | Needs a confirm step plus orphan cleanup (lifecycle rule on an unconfirmed prefix). |
| ADR-012 | **Privacy at source**: count-only input capture, blur before upload, domain truncation on device | Data that is never collected cannot leak; builds worker trust; eases compliance | Collect everything, filter server-side | Blurred screenshots can't be "un-blurred" for an investigation, which is intentional. |
| ADR-013 | **Electron** (required) with sandboxed renderer, typed zod-validated IPC, Fuses, signed updates | Brief requirement; shared TS/React; mature updater | Tauri (excluded by the brief); native per OS | Larger binary and memory footprint (~150MB RAM). Mitigated by lean renderer and lazy windows. *Signed updates: superseded for now by ADR-131 (builds are not code-signed yet).* |
| ADR-014 | **Browser extension + Native Messaging** for URL tracking | The only reliable cross-browser, cross-OS way to get the active tab URL/domain | Window-title parsing; OS accessibility APIs | Extension install friction (managed install via policy for orgs). Fallback heuristics remain. |
| ADR-015 | **Containers on AWS (ECS Fargate) + RDS PostgreSQL + ElastiCache + S3**, Terraform | Managed services cut operational load; S3-compatible storage keeps portability | Kubernetes (EKS); PaaS (Render/Fly); Vercel for web + separate API host | ECS is less portable than k8s. The web app may still go on Vercel (decide in Phase 2). |
| ADR-016 | **REST + OpenAPI generated from zod**; cursor pagination; RFC 9457 errors | Predictable public API; one schema source for validation, docs, and clients | GraphQL; tRPC | Less flexible querying than GraphQL. The report engine covers ad-hoc analytics. |
| ADR-017 | **Rollup tables maintained by projectors + nightly reconciliation**; matviews only where measured | Fast dashboards without an OLAP stack; correct under late/offline events | On-the-fly aggregation; ClickHouse/warehouse | Two representations must agree, so a drift metric and reconciliation job are required. Add a warehouse later if analytical load grows. |
| ADR-018 | **Money as integer minor units + ISO currency**; effective-dated rates; price snapshot at approval | Avoids float errors; reproducible invoices | Decimal numerics everywhere | Needs conversion helpers. Multi-currency FX is out of scope for v1 (one currency per invoice). |
| ADR-019 | **Roles as data (permission grants with scopes)**; the four built-in roles are presets | Custom roles later without a refactor; one evaluator serves reads, lists, reports, and widgets | Hard-coded role checks; external policy engine (OPA/Cedar) | We maintain our own evaluator. It can be swapped for Cedar later if rules grow complex. |
| ADR-020 | **SSE** for real-time (timer sync, presence, notifications) via Redis pub/sub | One-way push is all that's needed; works over HTTP/2 and proxies | WebSockets; polling | Separate endpoints are needed if bidirectional features arrive later. |
| ADR-021 | **Radix primitives + own styled components + visx charts** | Accessibility without importing someone else's visual identity; original design | shadcn/ui as-is; MUI; Ant Design; Recharts | More styling work up front, in exchange for a distinct, non-template look. |
| ADR-022 | **UUIDv7 IDs** (client-generated for agent events) | Time-ordered (index-friendly), globally unique offline, safe to expose | bigserial; UUIDv4; ULID | 16-byte keys. Acceptable. |

## Revision 2 — Supabase for database and file storage (2026-09-25, approved by product owner)

The app still runs on Vercel (Revision 1). The database and object storage move to **Supabase**. The ADRs below supersede the ones listed. Everything else stands.

| # | Supersedes | Decision | Reason | Trade-offs |
|---|---|---|---|---|
| ADR-110 | 103 | **Supabase Postgres** is the production database. It is reached through the **Session pooler** (Supavisor, port 5432) with the same `pg` Pool + `attachDatabasePool` code. No Supabase SDK is used for data access. PGlite is still used for tests and zero-setup local dev. | The product owner chose Supabase. The data layer is plain Postgres, so no code changed. | The direct host (`db.<ref>.supabase.co`) is IPv6-only unless the IPv4 add-on is bought, and Vercel can't reach IPv6. The transaction pooler (port 6543) is ruled out by ADR-111. Session pooling holds one server connection per client connection, so `max: 10` per function instance must stay within the Supabase plan's pooler limits. |
| ADR-111 | 104 (clarifies) | The app never queries as the table owner. Migrations run as `postgres`, then create a `tallywork_app` role (`NOLOGIN NOSUPERUSER NOBYPASSRLS`) and grant it to the login user. **Every pooled connection runs `SET ROLE tallywork_app`** on connect. Per-request tenant scope stays transaction-local (`set_config('app.org_id', …, true)`). | On Supabase the `postgres` role has `BYPASSRLS`, so FORCE RLS alone would not protect data queried as that role. A dedicated non-bypass role makes RLS apply. | `SET ROLE` is session-level, so it needs a pooler that keeps one server connection per client (session mode). This is why the transaction pooler is not supported. |
| ADR-112 | 106 | **Supabase Storage** (private bucket, default `tallywork`) replaces Vercel Blob. The API calls the Storage REST API with the service-role key (`SupabaseStorage` in `packages/api/src/lib/storage.ts`; no SDK). The bucket is created on first use (private, 50 MB file limit, image/PDF/CSV/XLSX only). The desktop agent uploads screenshots with **signed upload URLs** for one object path each (`method: 'supabase'`). Reads are still streamed through the authorized `/api/v1/media/:token` route. Vercel Blob and local file storage stay as fallbacks, picked by env vars. | Keeps database and files with one provider. The `Storage` interface meant only a new adapter and one desktop upload branch were needed. | Supabase signed upload URLs last a fixed 2 hours and can't set a per-object size limit (Vercel client tokens had 10 min and 8 MB). The bucket-wide 50 MB limit and MIME allowlist are the only upload guard. The service-role key bypasses Storage policies, so it must stay server-side. |
| ADR-113 | — | Supabase's auto-generated **Data API (PostgREST) is not used** and should be disabled, or the `public` schema removed from the exposed schemas. Auth stays in-house (ADR-101 routes). Supabase Auth is not used. | The app has its own auth, RBAC and tenant model. An unused public API is needless attack surface. RLS already returns no rows to it, because `app.org_id` is never set. | None. Re-enabling it later would need explicit per-role policies. |

## Money rules (Phase 9, 2026-09-25)

| # | Supersedes | Decision | Reason | Trade-offs |
|---|---|---|---|---|
| ADR-114 | — | **Money is integer minor units.** Time is priced **per billing entry** (one per approved time entry) as `round(seconds × hourly / 3600)`, **half-up** to the minor unit, and that amount is stored on the entry at approval. Invoice time lines are the exact sum of their entries' amounts; the unit price shown is the rate. **Tax is computed per line, half-up, then summed.** | Stored per-entry amounts make invoices, the Billing report and Amounts Owed reconcile to the cent, and a later rate change can never reprice approved time. | Half-up (not banker's rounding) can drift up by at most half a cent per entry; per-line tax can differ by a cent from tax on the total. Both are deterministic and shown on the invoice. |
| ADR-115 | — | **One currency per invoice** (the client's, else the organization's). Approved time or expenses in another currency are left out and counted in the preview (`other_currency_entries`). Payments must match the invoice's currency and client. No currency conversion. | Mixing currencies on one invoice produces wrong totals; conversion needs rates and rules that are out of scope. | A client billed in two currencies needs two invoices. |
| ADR-116 | — | **Rates are history.** A new rate closes the previous one from its start date. A rate that priced approved time is never deleted (deleting it is refused; superseding it before it started keeps it as an empty window). | Billing entries keep pointing at the rate they used, for audit and invoice unit prices. | The rates list keeps old rows. |

Each client has **four sections**, independently toggled: hours, tasks, activity, screenshots. **Hours and tasks default on; activity and screenshots default off**, and turning either of them on requires the admin's own grant to be **organization-wide** (`activity:read`/`screenshots:read` = `org`), not merely a manager's own-team scope. **No money is ever shown**: no rates, amounts, invoices or budgets in a currency — only tracked/estimate hours. **Screenshots are scoped to time worked on the client's included projects**: a screenshot surfaces only when its capture falls inside a desktop-tracked time entry (one with a `session_id`, so manual time never qualifies) on one of those projects, and is served through the same signed-media route (`mediaUrl` / `/api/v1/media/:token`) as every other screenshot, never a direct storage URL. Gating activity/screenshots behind the admin's own org-wide grant stops a team manager from exposing monitoring data they cannot even see in full themselves. Signed media keeps screenshot URLs from being guessable or reusable once revoked. | A revoked or expired `client_portal_access` row cannot be resent, only replaced (Task 8); resending is a follow-up. The worker notice is informational only — a worker cannot object to or change client visibility from the app. |
