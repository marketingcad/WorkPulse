### BUG-22 (Medium): a wrong period leaves the client stuck on an error

- **Module:** client portal dashboard (`/portal/[accessId]`).
- **Steps:**
  1. As a client viewer, open the dashboard.
  2. Clear the "From" date, or pick a start after the end, or a period over 93 days.
- **Expected:** the dates explain the problem, and the dashboard stays.
- **Actual:** the whole page became "From: This field is required · Try again". Try again resent the same period, so the client could not get back.
- **Root cause:**
  - `components/portal/portal-dashboard.tsx` sent every edit straight to the server. The browser's own date limits only apply in the calendar popup.
  - `app/portal/[accessId]/page.tsx` replaced the whole dashboard, date fields included, with the error.
- **Fix:**
  - The fields edit a draft, and only a valid period is applied.
  - A message beside the dates says what is wrong (`role="alert"`, `aria-invalid`).
  - The rule lives in one place: `PORTAL_MAX_RANGE_DAYS` and `portalRangeProblem` in `packages/contracts/src/limits.ts`, used by both the server schema and the browser. They sit in `limits.ts` so the page doesn't load every schema.
- **Verification:**
  - New Playwright test `a wrong period is explained beside the dates, and the dashboard stays`. It **failed on the old code** (screenshot showed the stuck error) and passes on the fix.
  - It also checks that no request is refused with a 400.
  - Contracts test `portal-range` checks that the browser rule and the server schema agree on 9 cases, including the 93-day limit.
- **Status:** Verified.

### BUG-27 (Low): the portal has no main landmark

- **Module:** client portal dashboard.
- **Steps:** open the dashboard with a screen reader, or press Tab and then Enter on "Skip to content".
- **Expected:** one main landmark holding the dashboard, which the skip link reaches.

- **Verification:** the portal smoke test now checks for exactly one main landmark containing the client's name, and that "Skip to content" takes focus and lands on `#main`. It **failed on the old page** (0 main landmarks) and passes on the fix.
- **Status:** Verified.

### BUG-28 (Low): Activity mixes two time zones

- **Steps:** a viewer in Manila opens a New York member's day.
- **Expected:** the timeline and the 10-minute blocks show the same times.
- **Actual:** the timeline said "Tracked, 4:32 AM – 4:40 AM" (Manila) and the block said 3:30 PM (New York), for the same work. The app timeline drawer also used the browser's zone.
- **Root cause:**
  - `components/tracking/activity-review.tsx` didn't pass the day's `timeZone` to `DayRibbon`, which then fell back to the browser's zone.
  - `components/tracking/spans-drawer.tsx` formatted times with no zone at all.
- **Fix:**
  - The timeline gets the day's zone.
  - The drawer shows times in the member's zone (the one the server uses to pick the day) and names it, for example "times in America/New_York".
- **Verification:** Playwright `activity-timezone` with the browser set to Manila. On the old code it failed with exactly round 6's text ("Tracked, 4:32 AM – 4:40 AM"); it passes on the fix.

### BUG-33 (Medium, new): the app day timeline always failed

- **Steps:** Activity › Apps › group by Member › Day timeline.
- **Expected:** that member's app spans for the day.
- **Actual:** "From: This field is required (and 1 more)". `GET /apps/spans` returned 400.
- **Root cause:** `packages/api/src/routes/time.ts` declared `/:kind{apps|urls}` before `/:kind{apps|urls}/spans`. Mounted under `/orgs/:orgId`, Hono sent `/apps/spans` to the usage handler, which needs a date range; `/urls/spans` happened to work. Reproduced with a minimal Hono app.
- **Fix:** four plain routes (`/apps`, `/urls`, `/apps/spans`, `/urls/spans`) with shared handlers. Same paths, same permissions.
- **Verification:**
  - API `activity-access` calls the real endpoint (400 before, 200 after).
  - Playwright "the app day timeline opens against the real server" failed on the old routes (400) and passes now.
  - Full API suite: 1206 passed.
- **Lesson:** the first BUG-28 test served the spans from the test itself, which hid this bug. Every endpoint a page depends on now gets at least one check against the real server.
- **Status:** Verified.

### BUG-32 (Medium): approved time with no pay rate is paid $0 with no warning

- **Steps:**
  1. A member has approved hours but no pay rate for those days.
  2. Run payroll, then finalize.
- **Expected:** the admin is told before the money is locked.
- **Actual:** the hours were added at $0 and nothing said so. Round 8: Wes's stub read "2h 14m · $31.06" with one unpriced hour inside. A finalized payroll cannot be changed.
- **Root cause:** `services/payroll.ts` `computeLines` summed `pay_amount_minor` (0 for an entry with no pay rate) and never checked the rate.
- **Fix:**
  - Each line now counts `unpriced_seconds` (approved entries with no pay rate) and is flagged `time_no_rate`.
  - Finalizing refuses with 422 `payroll_unpriced_time`, stating how many hours and whose, unless `confirm_unpriced: true` is sent.
  - The payroll page shows the hours on the line, in the warning box and in the finalize dialog. Confirming there sends the confirmation.
  - The audit entry records that it was confirmed.
  - The normal fix still works: set the rate, recalculate, and the hours are paid.
- **Verification:**
  - API `payroll-unpriced` (5 of 6 failed on the old code).
  - Playwright "approved time with no pay rate is shown before finalizing…".
  - `rates-effective-date` updated: its scenario finalizes unpriced time, so it now checks the refusal, then confirms.
- **Status:** Verified.

### BUG-31 (Low–Med): the Performance pages show old scores without saying so

- **Steps:**
  1. Approve a timesheet.
  2. Open Performance › Workers, then compare with Timesheets or Summary.
- **Expected:** the same hours, or a clear sign that the scores are not live.
- **Actual:** the Performance pages showed the earlier approved time, with no date or time. Every other screen showed the new figures.
- **Root cause:** the pages read scores stored by the daily job (`performanceDaily`, 03:15 UTC) or by an admin's Recalculate. Approvals update goals and achievements straight away but not scores (`services/performance-jobs.ts`). Meanwhile the desktop app's "My performance" computes the worker's score live, so the two disagreed. No page showed when its scores were from.
- **Fix:**
  - The five score endpoints return `calculated_at` (`services/leaderboards.ts`, `calculatedAt`).
  - Each page shows "Scores as of {time}. They update once a day, so time approved since then counts from the next update." (`ScoresAsOf` in `components/performance/ui.tsx`).
  - People who can recalculate are also told where. The Overview, which has the button, omits that hint.
  - Recomputing on every approval was rejected: it recalculates the whole organization for four period types, and approvals arrive in bursts.
- **Verification:**
  - API `performance-as-of`: the time is the same on all five pages; an approval leaves the scores and the time unchanged; Recalculate brings in the new hours and moves the time forward. It failed on the old code (`calculated_at` missing).
  - Playwright `performance-as-of` on the real server, as admin and as team manager.
- **Status:** Verified.

### BUG-24 (Low): "No approved timesheets" while the Approved tab loads, and the same on 11 other lists

- **Steps:** Approvals › Timesheets: from Pending (empty), open Approved.
- **Expected:** a loading state, then the approved timesheets.
- **Actual:** "No approved timesheets" for about 3 s. If Pending had rows, those rows showed under "Approved" instead.
- **Root cause:** the list kept the previous result on screen while the next loaded (`placeholderData: (p) => p`). That is meant for paging, but it also applied when the tab, a filter or the search changed. Twelve paged lists did the same: approvals, manual time, time entries, sessions, attendance, time off, tasks, expenses, invoices, payments, devices and the audit log.
- **Fix:** `useOrgPage` in `lib/api.ts` keeps the previous result only for another page of the same list (`samePagedList` in `lib/paging.ts` ignores `page` and `page_size`). Any other change shows the loading state. All 12 lists use it.
- **Verification:**
  - Web unit `paged-list`.
  - Playwright `paged-list-loading` holds back the Approved answer. On the old code it failed: the screenshot showed "No approved timesheets" on the loading tab. It passes now.
  - The specs of all 12 lists pass.
- **Status:** Verified.

### BUG-26 (Medium): approved time with no bill rate: "Approve timesheets first"

- **Steps:** a client's billable time is approved but has no bill rate; open New invoice for that client and period.
- **Expected:** a message that the time has no bill rate, and a way to set one.
- **Actual:** "Nothing to invoice in this period. Approve timesheets first…", with a link to Approvals, for time already approved.
- **Root cause:** time with no bill rate is worth 0, so it isn't invoiceable (`invoiceableTime` requires an amount above 0). The preview didn't say it existed, so the page assumed the time wasn't approved.
- **Fix:**
  - The preview returns `unpriced_bill_seconds`: billable, approved, uninvoiced time in the period with no bill rate (`services/finance.ts`).
  - The new-invoice page shows the existing "no bill rate" warning (`UnpricedTimeWarning`, as on Summary and the timesheet page).
  - When nothing else can be invoiced, it explains that the time has no bill rate and links to Rates instead of Approvals.
- **Verification:**
  - API `invoice-unpriced`: reported, then invoiced once a rate covers it, and limited to that client and to invoice managers. It failed on the old code.
  - Playwright: the new test in `invoices` failed on the old page and passes now.
- **Status:** Verified. The two options are: show time once each entry is approved (today), or only once the whole timesheet is approved.
