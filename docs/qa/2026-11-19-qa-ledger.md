### BUG-22 (Medium): a wrong period leaves the client stuck on an error

- **Module:** client portal dashboard (`/portal/[accessId]`).
- **Steps:**
  1. As a client viewer, open the dashboard.
  2. Clear the "From" date, or pick a start after the end, or a period over 93 days.
- **Expected:** the dates explain the problem, and the dashboard stays.
- **Actual:** the whole page became "From: This field is required · Try again". Try again resent the same period, so the client could not get back.
- **Root cause:**
  - `components/portal/portal-dashboard.tsx` sent every edit straight to the server. The browser's own date limits only apply in the calendar popup.
  - `app/portal/[accessId]/page.tsx` replaced the whole dashboard, date fields included, with the error.
- **Fix:**
  - The fields edit a draft, and only a valid period is applied.
  - A message beside the dates says what is wrong (`role="alert"`, `aria-invalid`).
  - The rule lives in one place: `PORTAL_MAX_RANGE_DAYS` and `portalRangeProblem` in `packages/contracts/src/limits.ts`, used by both the server schema and the browser. They sit in `limits.ts` so the page doesn't load every schema.
- **Verification:**
  - New Playwright test `a wrong period is explained beside the dates, and the dashboard stays`. It **failed on the old code** (screenshot showed the stuck error) and passes on the fix.
  - It also checks that no request is refused with a 400.
  - Contracts test `portal-range` checks that the browser rule and the server schema agree on 9 cases, including the 93-day limit.
- **Status:** Verified.

### BUG-27 (Low): the portal has no main landmark

- **Module:** client portal dashboard.
- **Steps:** open the dashboard with a screen reader, or press Tab and then Enter on "Skip to content".
- **Expected:** one main landmark holding the dashboard, which the skip link reaches.
- **Actual:** there was no `main` on the dashboard, loading or error states, so the skip link's `#main` target didn't exist.
- **Root cause:** `app/portal/[accessId]/page.tsx` rendered the dashboard in plain `div`s. Only the "not shared" state had a `<main id="main">`.
- **Fix:** the error, loading and dashboard states are each wrapped in `<main id="main">`. The signed-in toolbar stays outside, as page chrome. The shared `PortalDashboard` is unchanged: the admin preview already sits inside the app shell's `main`.
- **Verification:** the portal smoke test now checks for exactly one main landmark containing the client's name, and that "Skip to content" takes focus and lands on `#main`. It **failed on the old page** (0 main landmarks) and passes on the fix.
- **Status:** Verified.

### BUG-28 (Low): Activity mixes two time zones

- **Steps:** a viewer in Manila opens a New York member's day.
- **Expected:** the timeline and the 10-minute blocks show the same times.
- **Actual:** the timeline said "Tracked, 4:32 AM – 4:40 AM" (Manila) and the block said 3:30 PM (New York), for the same work. The app timeline drawer also used the browser's zone.
- **Root cause:**
  - `components/tracking/activity-review.tsx` didn't pass the day's `timeZone` to `DayRibbon`, which then fell back to the browser's zone.
  - `components/tracking/spans-drawer.tsx` formatted times with no zone at all.
- **Fix:**
  - The timeline gets the day's zone.
  - The drawer shows times in the member's zone (the one the server uses to pick the day) and names it, for example "times in America/New_York".
- **Verification:** Playwright `activity-timezone` with the browser set to Manila. On the old code it failed with exactly round 6's text ("Tracked, 4:32 AM – 4:40 AM"); it passes on the fix.
- **Status:** Verified.

### BUG-33 (Medium, new): the app day timeline always failed

- **Steps:** Activity › Apps › group by Member › Day timeline.
- **Expected:** that member's app spans for the day.
- **Actual:** "From: This field is required (and 1 more)". `GET /apps/spans` returned 400.
- **Root cause:** `packages/api/src/routes/time.ts` declared `/:kind{apps|urls}` before `/:kind{apps|urls}/spans`. Mounted under `/orgs/:orgId`, Hono sent `/apps/spans` to the usage handler, which needs a date range; `/urls/spans` happened to work. Reproduced with a minimal Hono app.
- **Fix:** four plain routes (`/apps`, `/urls`, `/apps/spans`, `/urls/spans`) with shared handlers. Same paths, same permissions.
- **Verification:**
  - API `activity-access` calls the real endpoint (400 before, 200 after).
  - Playwright "the app day timeline opens against the real server" failed on the old routes (400) and passes now.
  - Full API suite: 1206 passed.
- **Lesson:** the first BUG-28 test served the spans from the test itself, which hid this bug. Every endpoint a page depends on now gets at least one check against the real server.
- **Status:** Verified.

### OBS-9-1 (Low, not changed): an impossible date in the link

`?date=2026-13-45` passes the page's format check, so the server refuses it. The error shows inside the day panel and the day picker above it still works. Unlike BUG-22 the person isn't stuck, so the working code was left as it is. The two options are: show time once each entry is approved (today), or only once the whole timesheet is approved.
