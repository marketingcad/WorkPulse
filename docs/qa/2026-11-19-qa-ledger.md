### BUG-22 (Medium): a wrong period leaves the client stuck on an error

- **Module:** client portal dashboard (`/portal/[accessId]`).
- **Steps:**
  1. As a client viewer, open the dashboard.
  2. Clear the "From" date, or pick a start after the end, or a period over 93 days.
- **Expected:** the dates explain the problem, and the dashboard stays.
- **Actual:** the whole page became "From: This field is required · Try again". Try again resent the same period, so the client could not get back.
- **Root cause:**
  - `components/portal/portal-dashboard.tsx` sent every edit straight to the server. The browser's own date limits only apply in the calendar popup.
  - `app/portal/[accessId]/page.tsx` replaced the whole dashboard, date fields included, with the error.
- **Fix:**
  - The fields edit a draft, and only a valid period is applied.
  - A message beside the dates says what is wrong (`role="alert"`, `aria-invalid`).
  - The rule lives in one place: `PORTAL_MAX_RANGE_DAYS` and `portalRangeProblem` in `packages/contracts/src/limits.ts`, used by both the server schema and the browser. They sit in `limits.ts` so the page doesn't load every schema.
- **Verification:**
  - New Playwright test `a wrong period is explained beside the dates, and the dashboard stays`. It **failed on the old code** (screenshot showed the stuck error) and passes on the fix.
  - It also checks that no request is refused with a 400.
  - Contracts test `portal-range` checks that the browser rule and the server schema agree on 9 cases, including the 93-day limit.
- **Status:** Verified.

### BUG-31 (Low–Med): the Performance pages show old scores without saying so

- **Steps:**
  1. Approve a timesheet.
  2. Open Performance › Workers, then compare with Timesheets or Summary.
- **Expected:** the same hours, or a clear sign that the scores are not live.
- **Actual:** the Performance pages showed the earlier approved time, with no date or time. Every other screen showed the new figures.
- **Root cause:** the pages read scores stored by the daily job (`performanceDaily`, 03:15 UTC) or by an admin's Recalculate. Approvals update goals and achievements straight away but not scores (`services/performance-jobs.ts`). Meanwhile the desktop app's "My performance" computes the worker's score live, so the two disagreed. No page showed when its scores were from.
- **Fix:**
  - The five score endpoints return `calculated_at` (`services/leaderboards.ts`, `calculatedAt`).
  - Each page shows "Scores as of {time}. They update once a day, so time approved since then counts from the next update." (`ScoresAsOf` in `components/performance/ui.tsx`).
  - People who can recalculate are also told where. The Overview, which has the button, omits that hint.
  - Recomputing on every approval was rejected: it recalculates the whole organization for four period types, and approvals arrive in bursts.
- **Verification:**
  - API `performance-as-of`: the time is the same on all five pages; an approval leaves the scores and the time unchanged; Recalculate brings in the new hours and moves the time forward. It failed on the old code (`calculated_at` missing).
  - Playwright `performance-as-of` on the real server, as admin and as team manager.
- **Status:** Verified.

### BUG-64 (High): turning two-factor on leaves other sessions signed in

- **Steps:** sign in on two browsers and a desktop device with the password. On one browser, turn on two-factor.
- **Expected:** everything else is signed out: from now on, signing in needs the code.
- **Actual:** the other browser and the device stayed signed in. Someone who had the password and had already signed in kept access without ever giving a code.
- **Fix:** confirming two-factor signs out every other session and desktop device and keeps this one, like a password change (`confirmTotpSetup` in `services/mfa.ts`).
- **Verification:** API `auth-rules`.
- **Status:** Verified.

### BUG-65 (Medium): turning two-factor off, or an owner reset, leaves devices signed in

### BUG-69 (Medium): wrong passwords in the two-factor settings are free guesses

- **Verification:** API `auth-rules`: after 8 wrong passwords in the settings, signing in is refused.
- **Status:** Verified.
