# WorkPulse QA report: full pass, 19–23 November 2026

A feature-by-feature QA of WorkPulse: every feature was audited, tested, fixed where it failed, retested and covered by automated tests. The running record, with every bug's steps, root cause and fix, is the ledger: [2026-11-19-qa-ledger.md](2026-11-19-qa-ledger.md). The plan and the list of features are in [2026-11-19-feature-inventory.md](2026-11-19-feature-inventory.md).

## 1. Summary

- **Features:** 28 identified, 28 tested. Features 1–27 were tested one by one; feature 28 (navigation, layouts on every screen size, accessibility, page speed) is covered by the full browser suite (its navigation, responsive, accessibility and page-speed tests) and by the every-page audit on 24 November: 280 pages opened as 6 roles, with no findings (section 4).
- **Bugs:** 69 found and fixed (BUG-22 to BUG-94; BUG-25, BUG-29 and BUG-30 are not used in this ledger, and BUG-56 became a decision, below). 2 High, 27 Medium, 40 Low. One more issue from round 7 (OBS-R7-2, the desktop Submit with no feedback) was fixed too.
- **Open bugs:** none. One finding (BUG-56, pay rates in another currency than the organization's) was investigated and not changed: payroll supports pay groups in other currencies, so it is a product decision (C-40).
- **Decisions waiting on the owner:** 27 product questions (section 5). None blocks release.
- **Tests:** 83 test files were added or changed (section 4). In the final regression, 2,174 unit and API tests passed with none failing. Of 1,065 browser tests, 1,053 passed. The 8 that failed were rerun on their own: 7 were the test server's own rate limit and passed; 1 was a test with a date bug, which is fixed and passes (section 4).

The most serious bugs fixed:
- **BUG-60 (High):** time off already paid in a finalized payroll could be cancelled, leaving the pay wrong.
- **BUG-64 (High):** turning on two-factor sign-in left every other session and desktop device signed in with the password alone.
- **Medium, among others:**
  - sign-in and session security (BUG-65, 66, 69, 76);
  - people seeing data they shouldn't (BUG-90 the Overview's tasks, BUG-91 AI Insights after a team change);
  - money and time figures (BUG-32, 49, 53, 54, 57, 84, 87).

**About the 8 browser failures.**
- 7 were the server's rate limit, not product bugs. Accepting an invitation is limited to 20 per address per clock hour, and the limit is on in the browser tests, as in production. The suite accepts more than 20 invitations from one address. A run inside one clock hour (this one ran from :30 to :44) hits the limit; a run across the top of an hour doesn't.
- The 8th (the desktop manual-time refusal, BUG-23's test) was a test bug. It picked "this weekday last week" at 07:00. Today, a Monday, that was 23:00 on Sunday in UTC, which is the week before the approved one, so the server rightly accepted the request. The test now uses last week's Wednesday at midday.

**Known flaky test, now fixed:** `electron/timesheet-submit` (feature 7) read the organization's time zone from a field that doesn't exist, so it used the computer's own. On a computer ahead of UTC it asked for time "tomorrow" every day from 16:00 to 24:00 UTC. It reads the right field now and passes in that window; `web/finance-figures` had the same slip.

**Browser suite and the invitation limit, now fixed:** each person a test creates through the API accepts their invitation from their own address (`e2e/support/invitee.ts`), as real invitees do. The server's limit is unchanged. A full run inside one clock hour no longer hits it.

**Lower-priority observations** (not bugs, not changed) are listed at the end of each feature in the ledger. The ones most worth doing next:
- integrations: a connection whose sync fails is never synced again; fix before the first integration ships;
- the schedule editor drops split shifts made through the API;
- documents can be added to archived projects;
- the daily summary arrives in the evening in the Americas;
- the desktop app's manual-time form reads times on the computer's clock, while the server dates them in the person's profile time zone; when the two differ, early-morning time can land on the day before.

**Not tested in this pass:**

- real email delivery (the test server has no mail service);
